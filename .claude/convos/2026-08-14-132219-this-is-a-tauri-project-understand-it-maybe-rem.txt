● Good, that covers the key decisions. Here's the design, presented section by
  section.

  1. Architecture

  Build-time: a build script freezes the vendored better-adb-sync submodule into
  adbsync.exe via PyInstaller. That, plus adb.exe/fastboot.exe/DLLs from
  platform-tools-latest-windows.zip, get bundled as Tauri sidecar binaries —
  shipped inside the app, nothing for the user to install separately.

  Runtime: the Tauri (Rust) backend never talks to the phone directly — it
  shells out to the bundled adbsync.exe, always passing --adb-bin pointing at
  the bundled adb.exe (never relies on ambient PATH, per the researched
  footgun). One adbsync pull/push subprocess call per included top-level folder
  (never a whole-tree call with excludes — the confirmed permission-denied crash
  rules that out). Rust owns constructing every ANDROID/LOCAL path pair itself
  (always with the correct trailing slash) — the UI never lets the user type a
  raw path pair, closing off the nesting-duplicate bug at the source.

  Frontend: React + astryxdesign, driving device selection, per-folder
  classification review, and progress — calling Tauri commands that wrap the
  subprocess calls.

  Trade-off accepted: still shelling out to a subprocess rather than a native
  Rust ADB implementation, so adbsync's mtime-only diffing (no hash/integrity
  check) is inherited as-is for v1. That's consistent with your "shell out"
  answer — flagged again in testing/error-handling below since it's the main
  known gap.

  Does this architecture look right so far?

  - space::check(dest, estimated_bytes) — free-space preflight, and a

  - sync::run_backup(serial, dest, included_paths) / sync::run_restore(serial,

  1. App launches → lists connected devices via bundled adb.exe.
  2. User picks a device → no saved profile found → classify::suggest runs adb

  list.
  3. User reviews/edits the suggested list on the Classification screen, sets a
  destination folder.
  4. Profile (classification + destination) saved to the app-data JSON, keyed by
  device serial.

  Backup run:
  1. User hits Backup → preflight (space::check): free space vs. rough estimate,
  cloud-sync-path warning. Blocks start until resolved or explicitly
  acknowledged.
  2. sync::run_backup iterates the included paths one at a time (never a
  whole-tree call), spawning adbsync.exe pull per folder with the
  correctly-built trailing-slash pair.
  3. Each subprocess's --show-progress output is parsed and emitted as Tauri
  events → frontend updates a per-folder/per-file progress view.
  4. On completion of all folders, run marked done. Re-running later is the same
  flow — adbsync's mtime diffing makes it incremental automatically.

  Restore run: same shape in reverse — sync::run_restore pushes from the local
  destination back to the phone, reusing the same profile's path mapping.
  Because push/pull share the same "one call per included leaf path, app builds
  the pair" primitive, this is the same code path with source/dest swapped, not
  a separate implementation.

  Returning to an existing device: skip classification (profile already exists),
  go straight to the Run screen — user can still open Profile Settings to edit
  classification/destination if something changed.

  "something went wrong"), and leaves already-completed folders marked synced.

  plus the run_items history means it's safe and picks up where it left off,
  consistent with the research's confirmed incremental behavior.

  confirm-before-delete only — check against the device via adb shell ls before
  deleting anything locally, per the incident case study. No automatic deletion
